## Security

Advisory review (not a pentest). Coverage: all 25 files under `src/` via full reads of auth/api/toast/route files plus pattern sweeps for `{@html}`/innerHTML (0 matches), localStorage, `import.meta.env`/secrets, `eval`/`new Function`/`window.open`, and credential literals. Positive assurances: no raw-HTML sinks anywhere (all user/API content auto-escaped via Svelte text interpolation, e.g. `Toaster.svelte:28`); no hardcoded secrets/API keys; token sent via `Authorization` header (no cookie-based CSRF surface). The `payment/[token]` page cannot be audited — the route does not exist in `src/routes`; only endpoint constants reference payment tokens. **All findings are judgement calls — nothing is exploitable as coded without an external XSS or backend flaw.**

- **JC (medium) — JWT stored in localStorage, sent on every request** — `src/lib/services/api.ts:4` (read + auto-attach), `src/lib/stores/auth.ts:41` (`setToken` persists, no expiry/scoping). Any single XSS or compromised dependency exfiltrates a long-lived credential; also readable by extensions. Not exploitable as coded (no sink exists) — defense-in-depth (CWE-922).
- **JC (medium) — no auth guard anywhere in the `(app)` route group** — `src/routes/(app)/+layout.svelte:1–63`: anonymous visitors get dashboard/sessions UI with zero `$auth` check and no redirect; protection is entirely implicit in the API returning 401. Server-side authz remains the real boundary; the guard is absent rather than weak (CWE-602). The `(auth)` group also lacks the inverse guard.
- **JC (medium) — logout never revokes the server session; no UI path calls logout** — `src/lib/services/auth.ts:15–18` and `src/lib/stores/auth.ts:53–59` only clear localStorage and never call `/auth/logout` (`AUTH_LOGOUT`, `constants/api.ts:8`); neither implementation has any caller, so credentials persist in localStorage indefinitely (CWE-613).
- **JC (low) — API base falls back to hardcoded plaintext localhost** — `src/lib/services/api.ts:1`: deployed without `VITE_API_URL`, the app silently targets `http://localhost:3000/api/v1` (CWE-319).
- **JC (low) — no Content-Security-Policy on any document** — `src/app.html:2–13`: no CSP, Referrer-Policy, or frame headers; combined with the localStorage token, the first future XSS gets a direct path to token theft (CWE-693).
- **JC (low) — landing-page auth redirect is dead code** — `src/routes/+page.svelte:9–13` reads `$user.isAuthenticated` off the wrong store (`stores/auth.ts:34–37`); broken guard, not a bypass (CWE-602).
- **JC (low) — localStorage user blob parsed unguarded; expired tokens count as authenticated** — `src/lib/stores/auth.ts:23, 39–44, 66`: corrupted `user` value white-screens the SPA at module init; `isAuthenticated = !!token` treats garbage tokens as authenticated (client-side only); `setToken` sets `isAuthenticated:true` even when passed null/undefined (CWE-20).
- **JC (informational) — public payment page absent; payment endpoints keyed by participantId** — `src/lib/constants/api.ts:17–19` builds public payment URLs from raw `participantId`; whether those IDs are guessable is backend-owned (see backend Security axis).

**Security summary:** 8 findings — 0 hard violations, 7 judgement calls + 1 informational. Worst: the localStorage JWT (`src/lib/services/api.ts:4`, `src/lib/stores/auth.ts:41`) — harmless today only because no XSS sink exists; add CSP + token hardening before any raw-HTML feature lands.
